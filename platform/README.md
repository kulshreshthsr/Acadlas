# Acadlas platform

The shared backend every Acadlas product sits on: authentication and schools (Better Auth
organizations), and Acadlas School — students, guardians, classes, attendance, fees, staff,
reports and the audit trail.

Hono + TypeScript, Postgres on Neon via Drizzle ORM, auth via Better Auth's organization plugin.
Runs under Node. It can also run with no Neon at all, on a Postgres that lives inside the Node
process (PGlite) — handy offline, and what the tests use.

## Setup

```powershell
npm install
Copy-Item .env.local.example .env.local   # then fill in DATABASE_URL and BETTER_AUTH_SECRET
npm run db:push                           # creates or updates the tables in your Neon database
npm run dev                               # starts the API at http://localhost:8787
```

`BETTER_AUTH_SECRET` — any long random string. Generate one with:

```powershell
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
```

**No Neon?** Set `DATABASE_URL=pglite://.data/acadlas` in `.env.local`. The database is kept in
the `.data` folder (git-ignored) and its tables are created and updated every time the server
starts — no `db:push` needed.

## Multi-tenancy, in one paragraph

A school is an `organization`. A user's session carries an "active organization" — that's the
tenant for every request they make. Every `/api/school/*` request goes through `tenantGate()` in
`src/school/tenant.ts`, which reads the session, takes the school from it (never from the URL or
the body), re-checks on every request that the person is still a member, and turns their role into
a permission set. Every query then filters on `tenant.schoolId`. `npm test` includes a suite that
signs in as one school and tries to read, change and use another school's records by id — every
attempt must come back 404.

## Roles

| Role           | Can                                                                          |
| :------------- | :--------------------------------------------------------------------------- |
| Owner          | Everything. Whoever created the school.                                       |
| Administrator  | Everything, including settings, staff and fees.                               |
| Accountant     | Fees: plans, collecting, concessions, cancelling receipts, fee reports.      |
| Front office   | Admissions and student records, registers, collecting fees.                  |
| Teacher        | Registers and student records for the sections they are class teacher of,  |
|                | or teach a subject to. Can change only today's register.                     |

Owner, Administrator and Front office may also invite parents to the parent app (`parents.manage`).

## Parents

Parents are **not** members of the school — that would let them list its staff. They have their
own table (`parent_access`, one row per guardian), their own API (`/api/parent/*`, in
`src/parent/`) and a gate of its own that re-reads the session and their access on every
request.

- Staff invite a guardian from the student's record. The link is `<app>/parent/welcome#<secret>`;
  only the secret's SHA-256 is stored. The parent confirms the child's date of birth (five wrong
  answers kill the link) and sets a password. Their login is then phone number + password.
- A number that is already a parent elsewhere links only with that account's password. A link
  sent to an active parent resets their password and signs out every device.
- Phone numbers are set only by the activation code: a database hook in `src/auth.ts` refuses
  any web request that tries to set one, and the SMS routes are off until a provider exists.
- Settings → Parent app decides what parents see (off by default). A section switched off is
  refused by the API, not hidden by the screen. Revoking access, or changing a guardian's phone
  number, ends it at once.
- `src/test/parents.test.ts` attacks all of it: other families, other schools, leaked links,
  number takeover, cross-site use, leaks of internal fields.

They are Better Auth organization roles (so an invitation carries the role), mapped to
permissions in `src/school/roles.ts`, and checked on the server on every route.

## The outer defences

Every `/api` request passes these before any route runs (`src/app.ts`); `npm test` includes a
suite (`src/test/security.test.ts`) that attacks each one.

- **Only through the app's proxy.** In production the browser calls the app's own address and a
  Cloudflare Pages Function forwards to this API with `PROXY_SHARED_SECRET`. Requests without it
  get 403, and with `NODE_ENV=production` the server refuses to start unless it is set. The same
  value must be set on the Pages project.
- **One trusted client address.** Taken from the proxy (Cloudflare's `cf-connecting-ip`), never from
  a header the caller wrote (`src/lib/client-ip.ts`). Every rate limit keys on it; an IPv6 /64
  counts as one caller.
- **Rate limits.** Better Auth's limiter is always on (sign-in 20 a minute per address, sign-up 50
  an hour, school creation 5 an hour). On top: wrong passwords are counted per account — 10 per 15
  minutes from one address, 50 an hour from anywhere — so guessing one password is slow however
  many addresses are used. Plus a ceiling per address and per signed-in person.
- **Writes only from our pages.** `POST`/`PUT`/`PATCH`/`DELETE` under `/api/school` need an
  `Origin` from `CORS_ORIGINS`.
- **Small bodies.** 256 KB, or 4 MB for a student import.

The rate limits live in memory, which is right for one API process. Run more than one and they
must move to shared storage, or each process allows the full limit on its own.

| :---------------------- | :------------------------------------------------------------- |

| `npm test`              | API tests on an in-memory Postgres (no Neon needed)            |

## Email

Without `RESEND_API_KEY` and `MAIL_FROM`, invitation and password-reset emails are printed in the
API's terminal instead of sent. Invitations do not depend on email: the Staff screen shows each
invitation link to copy or send on WhatsApp.

## Not done yet, on purpose

- **Deploying.** It runs under Node (Render, Railway, Fly, a small VM). For Cloudflare Workers it
  needs a Workers entry file and either the paid plan or a lighter password hash — the free plan's
  10 ms CPU limit is too short for Better Auth's default password hashing.
- **Online fee payment** (Razorpay, Cashfree) — needs each school's merchant account.
- **Student logins, exams and report cards, timetable, transport** — later products and modules
  on this same platform.
- **Codes by SMS** for parents (first sign-in and password reset) — needs an SMS provider with DLT
  registration. Until then the school's link does both.
- **Email verification** is off until Resend is configured, so an account's email is not yet
  proven to belong to its owner, and sign-up says when an email already has an account. Turn
  on `requireEmailVerification` in `src/auth.ts` once mail is sent for real.
